# EvoData — корпоративний сайт

Статичний корпоративний сайт EvoData за ТЗ «Evo Data V1.1 без CMS».
Верстка виконана 1:1 з макета Figma.

**Стек:** Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · ESLint + Prettier.
Без CMS, бекенду, бази даних і серверної частини — увесь контент лежить у коді.

---

## Запуск

Потрібен **Node.js ≥ 20.9**.

```bash
npm install     # встановлення залежностей
npm run dev     # режим розробки → http://localhost:3000
```

## Збірка та продакшн

```bash
npm run build   # production-збірка
npm run start   # запуск зібраного застосунку → http://localhost:3000
```

Додаткові команди:

```bash
npm run lint         # ESLint
npm run typecheck    # перевірка типів TypeScript
npm run format       # форматування Prettier
```

### Заміна зображень

Файли лежать у `public/images/`. Достатньо покласти файл із тим самим ім'ям —
шляхи вказані у `src/content/en/*.ts`. Рекомендований формат — **WebP**.
Приклад конвертації (пакет `sharp` уже є в залежностях):

```bash
node -e "require('sharp')('in.png').resize(1800).webp({quality:85}).toFile('out.webp')"
```

### Іконки сайту

Next бере їх із `src/app/` за іменами файлів і сам додає `<link>` у `<head>`:

| Файл | Для чого |
| --- | --- |
| `icon.svg` | вкладка браузера в сучасних браузерах, `sizes="any"` |
| `favicon.ico` | 16/32/48 px, запасний варіант і прямий запит `/favicon.ico` |
| `apple-icon.png` | 180×180, іконка на домашньому екрані iOS |

**Джерело — `icon.svg`**, решта з нього генерується. Він векторний, тому
масштабується без втрат: еліпс із градієнтом плюс той самий контур «evo», що й
у логотипі шапки (`public/images/logo-evo.svg`), — не растр, який довелося б
перемальовувати під кожен розмір.

Кадр підігнано під іконку: у вихідному PNG замовника еліпс займав 93 % ширини
й 73 % висоти квадрата, тобто в 16 px від нього лишалася б крапка. У `icon.svg`
поле обрізане до самого еліпса, і він іде на всю ширину плитки.

Після зміни `icon.svg` перегенерувати растри:

```bash
node -e "
const sharp=require('sharp'),fs=require('fs'),VB=1914;
const render=s=>sharp('src/app/icon.svg',{density:Math.max(1,72*s*4/VB)}).resize(s,s,{kernel:'lanczos3'});
(async()=>{
  const sizes=[16,32,48], pngs=[];
  for (const s of sizes) pngs.push(await render(s).png({compressionLevel:9}).toBuffer());
  const head=Buffer.alloc(6); head.writeUInt16LE(1,2); head.writeUInt16LE(sizes.length,4);
  let off=6+16*sizes.length; const dir=[];
  pngs.forEach((p,i)=>{const e=Buffer.alloc(16);
    e.writeUInt8(sizes[i],0); e.writeUInt8(sizes[i],1); e.writeUInt16LE(1,4); e.writeUInt16LE(32,6);
    e.writeUInt32LE(p.length,8); e.writeUInt32LE(off,12); off+=p.length; dir.push(e);});
  fs.writeFileSync('src/app/favicon.ico', Buffer.concat([head,...dir,...pngs]));
  const mark=await render(152).png().toBuffer();
  await sharp({create:{width:180,height:180,channels:3,background:'#ffffff'}})
    .composite([{input:mark,left:14,top:14}]).png({compressionLevel:9}).toFile('src/app/apple-icon.png');
})();"
```

`apple-icon.png` — єдиний непрозорий із трьох: iOS зафарбовує прозоре чорним і
сам заокруглює кути, тому знак лежить на білому з полем у 14 px.

### Якість зображень

Файл у `public/` — не те, що бачить користувач: `next/image` перетискає його
під потрібну ширину, за замовчуванням у **AVIF з якістю 75**. Тобто стиснення
завжди подвійне, і саме друге вирішує.

Для фотографій і гладких 3D-об'єктів (герої, `principles.webp`) 75 не видно —
перевіряв покроково. Але дрібний регулярний растр AVIF на 75 змиває в пляму:
рендери слайдера на About Us вкриті сіткою з крапок, і вони помітно пливли.
Тому:

- вихідний файл кладемо **в рідній ширині оригіналу**, без попереднього
  зменшення (зайвий ресемплінг з'їдає ту саму дрібну деталь), і з високою
  якістю (`quality: 92`);
- на `<Image>` ставимо `quality={90}`. У Next 16 значення, відмінне від 75,
  треба спершу дозволити в `next.config.ts` → `images.qualities`, інакше
  оптимізатор мовчки округлить його до найближчого дозволеного.

Ціна — AVIF рендера виріс з 11 до 18 KB; Lighthouse не змінився.

### Телефон і e-mail: захист від спам-ботів

Значення лежать у **`src/config/contacts.ts`** — правити там, у звичайному
читабельному вигляді. Решта відбувається автоматично.

У віддану розмітку контакт потрапляє без `href` і спотвореним у три шари —
кожен доводиться знімати окремо (`src/lib/scramble.ts`):

1. **Перевернутий** (`moc.atadove@olleh`). CSS `unicode-bidi: bidi-override`
   розвертає його назад для ока.
2. **Без `@`, крапки і плюса** — саме вони роблять рядок схожим на адресу чи
   номер. У HTML на їх місці порожні `<span>`, а сам символ малює CSS
   (`.m-a`, `.m-b`, `.m-c` наприкінці `globals.css`). Збирачі адрес читають
   HTML, а не стилі.
3. **Із шумом.** Після кожних двох символів вставлено зайвий — не `display:
   none`, а обрізаний до нуля (`sr-only`): приховані елементи випадають з
   `innerText`, а обрізані лишаються, тож шум труїть і цей шлях теж. Бот, який
   усе-таки розверне рядок, забере правдоподібну, але неіснуючу адресу.

У підсумку в HTML немає ні `mailto:`, ні `@`, ні жодного рядка, схожого на
адресу чи телефон — перевірено `grep`ом по продакшн-збірці. Людина бачить
контакт правильно навіть із вимкненим JavaScript.

Так само порожній і **живий DOM**: саме́ по собі ніщо цього не розгортає, тож
скрапер, який виконує JavaScript і дочікується гідратації, забирає ті самі три
шари. Справжнє значення з'являється лише **після кліку**: `ContactLink` — це
кнопка, яка збирає контакт у браузері, кладе його в буфер обміну («Copied»),
друкує звичайним текстом і робить посиланням `mailto:` / `tel:`. Клік —
жест, якого краулер не робить; це і є межа між читачем і збирачем адрес.

Ціна — один зайвий клік перед дзвінком і те, що виділити контакт мишкою до
кліку не вийде (скопіюється спотворений рядок; для цього й кладемо в буфер
самі). Скрінрідер отримує кнопку з назвою «Show and copy the e-mail address»
(тексти — `common.contact` у `src/content/en/common.ts`), а після активації
фокус переходить на вже розгорнуте посилання й воно зачитується як звичайне.

Три правила, щоб не зламати:

1. **`src/config/contacts.ts` не можна імпортувати в `"use client"`-компоненти** —
   інакше значення потраплять у JS-бандл. Тому їх і немає в `site.ts`, який
   тягне за собою інтерактивна шапка.
2. У `Organization` (`src/lib/schema.ts`) навмисно **немає** `email` і
   `telephone`: JSON-LD — найлегша здобич для збирача. Назва, URL, адреса та
   профілі лишилися.
3. Значення контакту не може містити `~`, `^` чи `*` — ці три символи
   використані як заглушки для `@`, `.` і `+`.

### Відео

Покладіть файл у `public/videos/` і вкажіть шлях у `src/content/en/home.ts` → `video.src`.
Від цього значення залежить поведінка блоку:

- `src` порожній (типово) — **секція не рендериться на жодній сторінці**
  (постер у макеті — стокова заглушка);
- `src` заданий — секція повертається скрізь, де її розміщено (головна,
  What we do, Industries, About us): показується постер із кнопкою,
  за кліком вмикається програвач.

## Мультимовність

ТЗ вимагає **архітектурної** підтримки: активна одна локаль (`en`), але всі тексти
винесені у `src/content/<locale>/`, а перелік мов — у `src/config/i18n.ts`.
Щоб додати мову: створити теку контенту, додати локаль у конфіг і (за потреби)
загорнути маршрути в сегмент `[lang]`.

CLS скрізь 0. Решту балів на mobile стримує LCP 3D-об'єкта в героєві внутрішніх
сторінок (1600×1600). Зауваження до доступності два, обидва свідомі й на бал не
впливають: контраст `Let's talk` у футері (відкрите питання 1) і
`label-content-name-mismatch` на кнопках, чия назва навмисно не збігається з
написом — перемикач мови та контакти (див. «Телефон і e-mail»).

Дві правки, які найбільше вплинули на результат — варто пам'ятати під час розробки:

- **`sizes` має відповідати реальному розміру зображення на екрані.** Завищене
  значення змушувало браузер тягнути надто великий варіант: LCP 3.6 с, Performance 90.
- **`size-[%]` рахує відсотки окремо від ширини й висоти** контейнера, тому квадратний
  3D-об'єкт у героях внутрішніх сторінок був спотвореним. Правильно — `w-[%] aspect-square`.

Адаптивність перевірено на 320 / 375 / 768 / 1024 / 1440 / 1920 px — горизонтального
переповнення немає на жодній ширині.

## Відкриті питання до дизайну

1. **Контраст.** `Let's talk` у футері (`white/50` на `#4264F6`, 2.32) не проходить
   WCAG AA. Залишено як у макеті — потрібне рішення дизайнера.
2. **Картку Case Study** (node `9165:260211`) з блоку «We develop and implement custom
   AI solutions…» прибрано: у текстах замовника («Главная страница.pdf», п. 5) її немає,
   а вміст у макеті — демонстраційний. Якщо блок кейсів потрібен — потрібні реальні тексти.
3. **Відео**: у макеті стокове зображення-заглушка. Потрібен фінальний постер і файл відео.
4. **Рядок переваг у Hero** зміщений на +7px (поля 64/50). Вирівняно симетрично від 64px.
5. **Куди ведуть пункти підменю.** Підменю реалізоване (nodes `9247:100973`,
   `9254:101016`), але окремих сторінок під 8 підпунктів у макеті немає, тому всі
   ведуть на батьківський розділ (`/what-we-do`, `/industries`). Якщо планувалися
   окремі сторінки або якорі — потрібен список адрес.
6. **Кнопки героя** («Book a Discovery Call», «Contact Us» на What We Do): у макеті
   видно лише текст 18px без явних стилів заливки. Використано стилі з компонент-сету
   `9423:1785` — варто звірити з дизайнером.
7. **Вкладки на What We Do** (секція `9325:1161`). Реалізовано те, що видиме в
   макеті: вступний текст «MVP Development» і під ним три вкладки (`9329:4288`) —
   Founders, Business Owners, CTOs. Вертикальний сайдбар (`9330:5345`) і ще дві
   вкладки («Testing, Validation…», «Deployment…») у Figma приховані й тексту не
   мають — якщо вони потрібні, потрібен контент і рішення, як їх показувати.
8. **Четверта картка «The Business Value of AI Transformation»** (`9329:4246`).
   У макеті вона зветься `Predictive Analytics`, у текстах замовника
   («Industries.pdf», п. 3) — `Create a Sustainable Competitive Advantage`
   з іншим описом. Залишено варіант із макета; якщо правильний документ —
   потрібне слово замовника (і, ймовірно, інше фото).
9. **Заголовок героя Industries** — `iGaming development services` (з макета).
   У текстах замовника заголовка для цієї сторінки немає, а сторінка
   перелічує вісім галузей, серед яких iGaming не згадано. Схоже на
   заглушку — потрібен фінальний заголовок.
10. **Таблиця «Key factors we evaluate»** (FAQ, питання 3) у документі —
    двоколонкова таблиця «Factor / What we consider». У макеті таблиць немає,
    тому виведено списком означень (назва фактора + пояснення).
11. **Слайдер «AI Solutions for Business Growth…»** (nodes `9420:1382`…`9420:1452`).
    У макеті перемикання між 6 напрямами позначене лише написом «(SCROLL)» —
    решта 5 слайдів лишалися непоміченими. Напис прибрано, додано стрілки та
    індикатори. Якщо дизайн передбачає інший вигляд контролів — потрібен макет.
12. **Ілюстрації слайдів 03 і 04** (`Computer Vision`, `Speech Recognition`) у макеті
    однакові (той самий `imageHash`) — імовірно, заглушка. Потрібне окреме зображення
    для 04.
13. **Картки «We develop and implement custom AI solutions…»** (node `9165:260193`)
    свідомо відходять від макета: у Figma картка горизонтальна (вертикальне фото
    ліворуч, текст праворуч), реалізовано фото зверху й текст під ним — на замовлення.
    Наповнення — п'ять напрямів із «Главная страница.pdf», п. 5, фото надані окремо.
14. **Порядок секцій на Industries.** У макеті білий блок «Our custom solutions»
    стоїть **над** синім героєм (y=0 проти y=699), хоча на всіх інших сторінках
    герой перший. Оскільки шапка прозора зі світлим текстом, над білим блоком вона
    була б нечитабельною, тож реалізовано звичний порядок: герой → контент.
15. **П'ята картка «Custom AI solutions for business»** — `Data-Driven Decision
    Making`. У макеті (`9320:78046`) карток чотири, у текстах замовника
    («What we do.pdf», п. 4) — п'ять. Реалізовано п'ять; фото надані окремо.
16. **Заголовок «Everything you need to now»** у макеті (`9241:24297` і
